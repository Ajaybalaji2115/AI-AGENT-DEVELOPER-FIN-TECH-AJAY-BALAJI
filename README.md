# SphereFinance: Agentic Financial Assistant for Apple Inc.

SphereFinance is an AI Financial Assistant designed for Apple Inc. It leverages structured SQL databases, semantic RAG search over PDF filings, and mathematical tools to answer financial queries. The system enforces strict, pre-retrieval Role-Based Access Control (RBAC) boundaries across different roles (Analyst, CTO, CEO) and maintains a persistent feedback loop (Correction Memory) inside SQLite.

---

## 🛠️ System Architecture

The assistant implements a genuine **tool-calling agent workflow** rather than a simple search-and-response chatbot. It follows a multi-tier authorization and routing process:

```text
                               USER
                                 ↓
                           Web UI / CLI
                                 ↓
                         API (Flask Server)
                                 ↓
                        Pre-Query Guard (RBAC)
                        - Scans text concepts
                        - Blocks unauthorized terms
                                 ↓
                              AI AGENT
                                 │
           ┌─────────────────────┼─────────────────────┐
           ↓                     ↓                     ↓
        SQL Tool              RAG Tool             Calculator
   (Validates Query)     (Pre-Retrieval Filter)   (AST Allowlist)
           ↓                     ↓                     ↓
     [SQLite - Excel]      [Chroma - PDF]         [Math Utility]
```

### 1. Ingestion Pipelines
- **Spreadsheets (Excel/CSV):** Structured spreadsheets containing income statements, headcount, and compensation metrics are parsed and inserted directly into structured SQLite database tables (`data/processed/financials.db`). Only relational SQL is used for metrics lookup.
- **Filings (PDF):** Unstructured annual reports are parsed page-by-page. Text paragraphs are embedded using SentenceTransformers and stored in a ChromaDB vector store collection (`financial_data`).

### 2. Precomputed Understanding Layer
To prevent expensive preprocessing overhead, high-level structural metadata is precomputed and saved in `/understanding`:
- `document_metadata.json`: Mapping files to classifications and formats.
- `financial_schema.json`: SQLite database tables and columns schema dictionary.
- `metrics.json`: Direct facts cache.
- `summaries.json`: Document outlines and highlights.

### 3. Pre-Retrieval RBAC & Security Design
Permissions are enforced **at the database query boundaries before data leaves the storage layer**:
- **Pre-Query Guard:** Intercepts raw user questions. If an Analyst or CTO queries restricted concepts (like "headcount" or "compensation"), the request is immediately blocked, preventing indirect leaks (e.g. CTO asking to "calculate revenue per employee").
- **SQLite SQL Guard:** Sanitizes SQL queries generated by the LLM. It blocks modifications (rejects `INSERT`/`DROP`/`ALTER`), ensures allowed table scopes, and prevents CTOs from reading headcount rows in the operational database.
- **Chroma RAG Guard:** Encodes role permission levels directly into ChromaDB queries using metadata tags:
  `where={"classification": {"$in": ["PUBLIC", "INTERNAL_OPERATIONS"]}}`

### 4. Safe AST Calculator
Unrestricted Python `eval()` is prohibited. Instead, the Calculator Tool parses formulas to an Abstract Syntax Tree (AST) and evaluates them recursively against a strict allowlist of operators (`+`, `-`, `*`, `/`, `%`, brackets). Any attempt to write code, call functions, or inject scripts is blocked.

### 5. Persistent Feedback Loop (Correction Memory)
User corrections are stored in a relational `feedback` table inside the SQLite database. Before processing a new query, the system runs a local semantic search over past negative corrections. If a similar question exists, the correction is retrieved and injected as a strict directive into the LLM synthesis context.

## 🚀 Installation & How to Run

### 1. Prerequisites
Install all core libraries:
```bash
pip install Flask flask-cors pandas openpyxl pdfplumber requests sentence-transformers chromadb reportlab python-dotenv
```

### 2. Configure Credentials (Optional)
Create a `.env` file in the root workspace folder:
```ini
GEMINI_API_KEY=your_google_gemini_api_key
```
*Note: If no API key is specified, the agent runs in **Demo Fallback Mode - Offline Agent Simulation** which performs rule-based planning, selects the same tools, and demonstrates the exact same security checks.*

### 3. Build Databases & Indexes
Run the pipeline to download resources, build SQLite, and run Chroma indexing:
```bash
python download_data.py
python backend/setup_sqlite.py
python backend/ingestion.py
python backend/understanding.py
```
This writes files inside `data/processed` and `understanding/`.

### 4. Start the Application
Start the backend server:
```bash
python -m backend.app
```
Access the dashboard in your web browser: **[http://127.0.0.1:5000](http://127.0.0.1:5000)**.

## 📈 Scalability to 100× Data Size

To scale this system to handle 100× the current volume of reports and spreadsheets (e.g. 300 annual filings and 500 compensation sheets):

1. **Database Layer migration:**
   - Migrate SQLite to **PostgreSQL**. This supports concurrently handled connections and connection pooling (via pgBouncer).
   - Leverage **TimescaleDB** if indexing financial metrics as chronological timeseries data.
2. **Vector Store Scaling:**
   - Replace ChromaDB with **pgvector** inside PostgreSQL or use standalone clusters like **Pinecone** / **Qdrant**.
   - Create partitioned indices based on security levels (a separate public index and a separate confidential HR index) rather than using a single index with filter arguments, ensuring complete physical isolation.
3. **Optimized PDF Chunk Ingestion:**
   - Run chunk parsing asynchronously using workers (e.g. Celery / Redis) to process page-by-page extractions.
   - Use GPU clusters to speed up SentenceTransformer embedding generations.
4. **Enhanced SQL Sanitation:**
   - Use an AST-based SQL parser (like `sqlglot`) to compile database queries generated by the LLM and mathematically verify that no columns or tables outside the role's allowlist are present, removing the risk of parser evasion.

## ⚠️ Known Limitations & Future Improvements
- **Keyword Concept Scanner:** The pre-query guard blocks indirect access by searching for concept keyword patterns. While robust for standard queries, it can be bypassed using highly abstract synonym phrasings (e.g., "calculate revenue divided by the sum of human resources"). With more time, a small classifier model (or a fast local LLM guardrail) could check semantic alignment against restricted concepts rather than relying on keywords.
- **Tabular PDF Data:** Simple text parsers can scramble multi-column tables in PDF pages. Using a structured layout model (like LayoutLM or AWS Textract) would preserve the formatting of financial tables in PDF reports.
